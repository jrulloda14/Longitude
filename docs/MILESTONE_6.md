# Milestone 6 - Meeting sharing, calendar export and contextual DST

October 20, 2026. **Implemented; shared tests, Windows native checks and both Mac CI targets verified. Performance acceptance remains open. Stop before Milestone 7.** The results below are separate from physical Mac acceptance and distribution certification. No release is published.

## Audit and implementation

The [mandatory audit](evidence/milestone-6/AUDIT.md) started at clean `935e67f92f55d9091b4bbea65015f723c319bd1d`, synchronized with GitHub. It reviewed the accepted plan, Windows/Mac reports, native/platform contracts, persistence and tests before code changes. Fresh baseline: **696 unit, 84 browser, 33 Rust tests passed**, typecheck/format passed. The approved optimized Windows executable was retained for comparison. Before screenshots are fresh captures at fixed instants, not replacements for failed after-images.

Existing `lib/share.ts`, MeetingSummary, DstNotice, Platform and Rust host were extended. There is one React frontend, one canonical selected instant, the same IANA/timezone and scheduling engines, and the same Milestone 4 schema/repository/CAS/recovery. No Milestone 7 work, external calendar integration, OAuth, accounts, server, telemetry or release publication was added.

- The summary shows editable title, selected reference date/time, exact duration, every participant's local start/end dates and times, IANA zone, offset/abbreviation/runtime standard or daylight name, and full-duration working-hours compatibility. Custom participant labels and ordering are retained. It never implies confirmed calendar availability.
- Four copy modes (full summary, one-line chat, local participant times, UTC) copy their actual preview. Native Windows/macOS use the same fixed clipboard command; browser fallback remains usable. Feedback is inline in the existing sheet.
- UTC ICS now validates input, escapes text including lone CR, folds at 75 UTF-8 octets, preserves Unicode, uses CRLF and cryptographic session identity, and sets real export/creation timestamps. Explicit New event changes identity; editing/reopening retains it.
- The existing weekly option has an explicit UTC/reference-wall basis, preserved through sheet reopening. The original selected fold instant is retained; subsequent gaps/folds use the established compatible policy. Reference-wall exports use bounded UTC RDATEs, including the initial occurrence for parser interoperability; no second timezone system or VTIMEZONE generator. This follows the latest explicit UTC DTSTART/DTEND requirement and is a documented adjustment to the earlier TZID proposal.
- Contextual notices explain actual upcoming changes, selected-date versus today's offsets, changes during a meeting, half-hour shifts and wholly skipped dates. Existing direct-entry gap/fold warnings and alternate-fold choice remain intact. The misleading selected-date word "now" was removed from the planner notice.
- Native Save uses an owned OS dialog, permits only calendar export, and atomically writes only the user-selected `.ics` destination. Normal cancellation, browser download initiation and post-selection failures have distinct outcomes. Duplicate Save is rejected; Quit waits until Save finishes/cancels.

Specification, policy and limitations: [ICS_EXPORT.md](ICS_EXPORT.md). Exact [changed-file inventory](evidence/milestone-6/modified-files.json) and [verification summary](evidence/milestone-6/verification-summary.json) compare against `935e67f`. Application source: `d53821df0a8098465523a70b4b71cf50d15af3fe` (initial implementation `76b3fab`; session-basis/skipped-date follow-up `89b8034`; WebKit modal-tab correction `d53821d`). Later documentation/evidence commits do not alter that tested implementation.

## Performance observations and historical CPU investigation

The fresh approved-5B baseline trial uses the exact retained optimized executable `d5d729feb3d43a08946b273a93457bf0f9c28c10ff6f576f9b3330911d405337`: **0.8393% live / 0.2395% planning total-machine CPU**, sampled private peaks **215.6875 / 218.671875 MiB**. It uses a 60-second warmup and nominal 120-second windows with no concurrent build/test suite. [Raw baseline](evidence/milestone-6/baseline/native-performance.json) records actual intervals, process sets, hardware, renderer metrics and drag/frame proxies.

This first baseline trial did **not reproduce** the historical 5A **9.0599% / 1.7754%** CPU result. That historical binary/source and measurement context differ; one lower sample is not proof of a fix or evidence that the old finding was false. The final M6 trial is **4.8013% live / 2.8925% planning CPU**, both **Fail** against the provisional <=1% / <=0.25% targets; private peaks **213.9336 / 220.4844 MiB** are below 250 MiB. Event-to-frame p95 is **2.4ms**, commit/frame proxy p95 **39.2ms**, frame p95/max **41.9/45.8ms**, zero Long Tasks and **59/59** captured outside moves. The frame budget also fails this trial; functional capture success is separate. [Raw final trial](evidence/milestone-6/native-performance.json).

Related-build browser/GPU/V8 profiling is recorded in [PERFORMANCE.md](PERFORMANCE.md) and [raw diagnostic](evidence/milestone-6/historical-build-profile.json): 4.3318% browser-subprocess CPU live, 3.4150% with the pulse temporarily paused, 1.8324% planning; 98.06% JavaScript idle samples. This supports animation/compositing and browser/native-event overhead as contributors, not a proven root cause. That profile uses the retained final 5A executable, not the unavailable exact historical measured binary. No animation removal, target relaxation, new worker or major performance rewrite was applied.

The [repeat of the exact approved-5B executable](evidence/milestone-6/baseline-repeat/native-performance.json), using the same instrumented conditions, measures **4.6059% live / 2.8825% planning**, private peaks **209.8672 / 212.7148 MiB**, renderer task **19.4413 / 6.9524 ms/s**. It also fails both CPU and frame budgets: frame p95 **43.4ms**, commit/frame p95 **42.1ms**, event/frame p95 **2.5ms**, no Long Tasks, **59/59** captured outside moves. M6 renderer work is effectively similar (19.3939 / 6.9762), frame/drag proxies are similar or slightly lower, memory increases by 4.0664 / 7.7695 MiB, and CPU differs by +0.1954 / +0.0099 percentage points. These single sequential trials do not establish a statistically significant M6 regression or certify unchanged performance. They demonstrate the high-cost condition also exists in approved 5B and that the first lower baseline is not a reliable performance guarantee. Motion remained enabled in both repeat/final trials. CPU/frame acceptance is explicitly **Fail/open**, not waived because functionality passes.

M6 summary/recurrence work runs in the mounted share sheet and memoized builders, not on clock animation frames. I/O runs only on explicit copy/export actions; filesystem work uses a blocking worker thread. Live/planning state separation, pointer capture, widget synchronization, persistence and scheduling search remain covered by regressions. Resource estimates and event-to-frame proxies are not input-to-photon or statistical certification. Mac resource measurements remain Blocked, with no Windows/CI substitution.
